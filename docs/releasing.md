# Releasing

Downloads are built by GitHub Actions ([release.yml](../.github/workflows/release.yml)), never on a
developer's machine, and every file carries a build-provenance attestation. A push to the `release`
branch builds everything and drafts a GitHub Release, and a person publishes it.

## What a release contains

| File | Built by |
|---|---|
| `tanki-skin-studio-<version>-macos-universal.dmg` | [packaging/macos/package.sh](../packaging/macos/package.sh): Apple silicon and Intel joined with `lipo`, the app and the CLI in one `.app` |
| `tanki-skin-studio-<version>-windows-<x64\|arm64>.msi` | [packaging/windows/package.ps1](../packaging/windows/package.ps1) with [tanki-skin-studio.wxs](../packaging/windows/tanki-skin-studio.wxs) (WiX v5): installs for the current user without administrator rights, Start menu shortcut, uninstall in Settings → Apps, newer versions replace older ones |
| `tanki-skin-studio-<version>-windows-<x64\|arm64>-portable.zip` | the same script: `tanki-studio.exe` and `tanki-cli.exe` with the C runtime linked in, and the licences |
| `SHA256SUMS.txt` | the release job |

Every download carries the licences: `LICENSE.txt` (GPL-3.0-or-later), the fonts' and icons'
licences, and `THIRD-PARTY-LICENSES.html`, the notices of every Rust crate built in, generated by
[cargo-about](https://github.com/EmbarkStudios/cargo-about) from `Cargo.lock`
([packaging/about.toml](../packaging/about.toml)). The release notes say where the full source is.

Release builds use no build cache, so nothing cached by another branch can reach a published file.

## Cutting a release

1. In a pull request, set the version in the workspace `Cargo.toml` (`[workspace.package] version`)
   and move the `Unreleased` notes in [CHANGELOG.md](../CHANGELOG.md) under that version; do the
   same in Russian in [CHANGELOG.ru.md](../CHANGELOG.ru.md) (same headings in Russian: Добавлено,
   Изменено, Исправлено). Merge it.
2. Point `release` at the merged `main` (this needs the signing secrets; without them, run the
   workflow manually from `main` instead):

   ```sh
   git push origin main:release
   ```

3. The **Release** workflow builds both platforms and creates the draft release `v<version>` with the
   files, their checksums and the notes from [packaging/release-notes.sh](../packaging/release-notes.sh):
   the version's CHANGELOG section under "What's new", its CHANGELOG.ru.md section under
   "Что нового" (the app shows the one of its interface language, English when the Russian one is
   missing; the script then warns), then [packaging/release-notes.md](../packaging/release-notes.md).
   Keep the English section first and both as `## ` headings: copies up to 0.3.0 read only the
   first "What's new" section and stop at the next `## ` heading.
   Pushing `release` again replaces the files of the same draft.
4. Download the files from the draft, try them on a Mac and on Windows, then press **Publish
   release**. Publishing creates the tag. A published version is never rebuilt: the next release
   raises the version.

Publishing also posts the release to the Telegram channel ([below](#announcing-in-telegram)).

Once a release is published, every installed copy older than it offers it at its next start
(at most every twelve hours). To try that path on an installed copy before the next release, start it
with `TANKI_PRETEND_VERSION=0.0.1`: it then takes itself for that version, offers the current
release, and **Update and restart** installs it over itself. The update only installs a file the
release's `SHA256SUMS.txt` lists, so a release must always carry it.

A manual run (**Actions → Release → Run workflow**) can name a test version such as `0.2.0-rc.1`;
it drafts a pre-release. A pull request that changes packaging builds both platforms without
drafting anything, and its files can be downloaded from the run.

## Announcing in Telegram

When a release is published, the **Telegram** workflow
([telegram.yml](../.github/workflows/telegram.yml)) posts it to the channel
[@tankiskinstudio](https://t.me/tankiskinstudio), from its [CHANGELOG.ru.md](../CHANGELOG.ru.md)
section only: «🚀 Tanki Skin Studio <version>», a line saying the app offers the update itself,
the headline of each change under ✨ Новое, 🔄 Изменено and 🐞 Исправлено (its bold lead kept
bold, cut at the first ":" or ". " as About cuts it), the `#обновление` tag, and two buttons:
**⬇️ Скачать** (the release page) and **📋 Все изменения** (CHANGELOG.ru.md at the release's tag).
The link preview is off. A version with no Russian section is not posted: the run warns instead.
Only publishing posts, so a draft never does, and a pre-release is skipped. The post is built by
[packaging/telegram-post.py](../packaging/telegram-post.py), which escapes every value for
Telegram's HTML and drops the last headlines rather than go over Telegram's 4096 characters.
`cargo xtask telegram` (part of `cargo xtask ci`) builds the post of every version in
CHANGELOG.ru.md and checks it fits. To see a post without sending anything (`--json` prints the
Bot API request):

```sh
packaging/telegram-post.py 0.5.0 --dry-run
```

The workflow posts with plain `curl` to the Bot API, with no third-party action; curl reads the
token from its standard input, so it is in no command line and no log. Set it up once:

1. In Telegram, open [@BotFather](https://t.me/BotFather), send `/newbot`, and give it a name and a
   username. It answers with the bot's token. Keep it secret: anyone with it can post as the bot.
2. In the channel, open **Administrators → Add Admin**, find the bot by its username, and leave it
   only **Post Messages**; turn every other right off.
3. In **Settings → Environments → release**, add two secrets:

   | Secret | Value |
   |---|---|
   | `TELEGRAM_BOT_TOKEN` | the token from @BotFather |
   | `TELEGRAM_CHAT_ID` | `@tankiskinstudio` |

   Without either one the workflow warns and posts nothing. If the environment requires a reviewer,
   the post waits for that approval like the release builds do.
4. To post a release again, or to try the setup, run **Actions → Telegram → Run workflow** with the
   version. With **Dry run** it shows the post in the log and posts nothing.

If the bot's token leaks, send `/revoke` to @BotFather and replace the secret.

## Verifying a download

```sh
sha256sum -c SHA256SUMS.txt
gh attestation verify tanki-skin-studio-0.1.0-macos-universal.dmg -R YuraZakaryan/tanki-skin-studio
```

## Signing

The build scripts sign when the secrets are there and warn and ship unsigned when they are not, so
test builds keep working. On the `release` branch a missing secret fails the build instead: a
release from `release` is always signed. Until the certificates exist, release with a manual run
of the workflow from `main` (unsigned).

The secrets belong to the **`release` environment** (**Settings → Environments → release**; it
appears after the first run, or create it). Pull requests build without that environment, so their
downloads are never signed.

### macOS: Developer ID and notarization

[packaging/macos/import-cert.sh](../packaging/macos/import-cert.sh) imports the certificate into a
temporary keychain; [package.sh](../packaging/macos/package.sh) signs the CLI and the app with the
hardened runtime ([entitlements.plist](../packaging/macos/entitlements.plist), empty), notarizes the
app and the `.dmg` with `notarytool`, staples the tickets and checks them with `spctl`.

1. Join the [Apple Developer Program](https://developer.apple.com/programs/enroll/) (99 USD a year;
   an individual account is enough).
2. In **Certificates, Identifiers & Profiles**, create a **Developer ID Application** certificate,
   install it in Keychain Access, and export it with its private key as a `.p12` with a password.
3. At [account.apple.com](https://account.apple.com), create an **app-specific password** for
   notarization. The **Team ID** is in the membership details.
4. Add to the `release` environment:

   | Secret | Value |
   |---|---|
   | `APPLE_CERTIFICATE` | the `.p12`, base64: `base64 -i DeveloperID.p12 \| pbcopy` |
   | `APPLE_CERTIFICATE_PASSWORD` | the `.p12` password |
   | `APPLE_ID` | the Apple ID email |
   | `APPLE_PASSWORD` | the app-specific password |
   | `APPLE_TEAM_ID` | the Team ID |
   | `KEYCHAIN_PASSWORD` | optional; random when unset |

### Windows: Authenticode

[packaging/windows/sign.ps1](../packaging/windows/sign.ps1) signs `tanki-studio.exe` and
`tanki-cli.exe` before they are packaged, then the `.msi`, with a timestamp, and verifies the
signatures. It takes either:

- **a code-signing certificate** as a `.pfx` (for example from Certum or another certificate
  authority; an open-source or OV certificate): `WINDOWS_CERTIFICATE` (the `.pfx`, base64) and
  `WINDOWS_CERTIFICATE_PASSWORD`; or
- **[Azure Trusted Signing](https://azure.microsoft.com/products/artifact-signing)**
  (open to organisations and, for individuals, only in some countries): `AZURE_TENANT_ID`,
  `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_SIGNING_ENDPOINT`, `AZURE_SIGNING_ACCOUNT`,
  `AZURE_CERT_PROFILE`. The signing client is pinned by version and SHA-256.

A new certificate earns SmartScreen's trust as people download signed files, so the first signed
releases may still show a SmartScreen notice.

The installer's `UpgradeCode` in `tanki-skin-studio.wxs` links every version together, so a new
`.msi` replaces the old one. It must never change.

## Protecting the `release` branch

Add a ruleset for `release` like the one for `main`: restrict creation, updates and deletion to
repository admins, and block force pushes. Only a maintainer can then start a release.
